# Seam audit, 2026-09-19

**TL;DR:** the package declares **16 seams** — 15 `Protocol`s and one `ABC`.
Ten earn the three-consumer rule outright; six stand under it and five now
state why. One states nothing and has no consumer and no implementer
(`sample.hmc.Kernel`, #790). The finding that matters for #813 is not any one
seam: **six seams are named by a module that defines a problem, and the other
ten are shared machinery reached only by shared machinery**, so the intents
`#813` wants called the same way across problems — simulate, bound, sample,
initialize — have no seam that spans them. Read from
`infra/appraise_seams.py` on `main` at `e795a73`.

## What the survey reads, and what it cannot

Consumer counts come from `infra/gate_new_seams.py` rather than a second
implementation, so the gate and this audit cannot disagree about what a
consumer is. That definition is **a module whose source names the seam**, and
it has a blind spot this audit found rather than assumed:

**A seam reached through a registry or an enum of names is undercounted.**
`likelihood.schedule.MessageSchedule` has five implementers and one module
naming it, because callers reach it through `MessageScheduleName`, which
`likelihood.message_passing` re-exports. The base's own module is imported by
two. Neither count is wrong; both are answering a narrower question than "how
many modules call through this seam". This matters beyond one row: the fix
#813 proposes for the overlap rows is repeatedly *a registry keyed by name* —
one annealing driver, a `METHODS` mapping for the seven `run_*` wrappers — and
every one of those would produce a seam that looks unearned to the gate. The
gate is right to count what it counts on a branch; the audit says the number
cannot be read as reach.

The "problems" column is the same kind of measure: a problem is reached when a
module that **is** that problem (`PROBLEMS.md`'s Defines column) names the
seam. A seam used by an optimizer that every problem uses reaches them all and
reads as reaching none.

## The decision per seam

**Earns it and stays, unchanged (10).** `Environment`, `Objective`, `Run`,
`EmissionFamily`, `Metrics`, `TempSchedule`, `Surrogate`, `TrainablePolicy`,
`Initializer`, `Channel`. Each is named by three or more modules.

**Stands under the rule with a reason, and the reason holds (5).**
`CountEmissionFamily` (1 named, 16 importing its module: it narrows
`EmissionFamily` for the families that carry a count, and the narrowing is
what a caller dispatches on); `KeyedMove`; `Policy`, which `TrainablePolicy`
extends; `RelaxedObjective`; and `MessageSchedule`, whose reason this audit
added — the count is the registry artefact above, not an absence of callers.

**Stands under the rule with nothing said (1).** `sample.hmc.Kernel`: no
consumer, no implementer, two modules importing its module for other names.
#790 already asks for a consumer or its removal; this audit supplies the
number that settles it, and #813's PR 3 removes it unless #790 gives it one
first.

**One to watch rather than act on.** `learn.relaxed.RelaxedObjective` has two
implementers, no consumer and no module importing its own. A seam with
implementers and no callers is a contract kept by its implementations for a
caller that does not exist; it is left as it is here because the relaxation
work (#211, Stage 5) is where that caller would come from, and deleting a
seam to add it back is not a saving.

## What #813's folds land on

The four folds need a seam each, and three of the four have none today:

- **The eight Python paths above a compiled kernel** already have theirs:
  `snakes_and_ladders.backend.Backend`, which `alpha_expansion` shows the
  shape of. The row counts twin *files*, so it is not eight call sites:
  `convolutional` and `message_passing` already dispatch on the enum and the
  twin is the implementation behind it; `maxflow`, `count_pairs` and
  `spatio_sequential` name their twin in prose alone, so a caller picks the
  module, and those three are the fold. `pruning_torch` is refused on the
  measurement: 1,613.4 ms to import against its oracle's 89.5 ms, 18.0×, on
  the path validation runs, and 7 package modules import it. It is not a twin
  behind a seam but the differentiable method, and it is recorded as the
  third outcome above — a difference that is a property of the method.
- **The four annealers** have `TempSchedule` for the schedule and nothing for
  the driver. One driver over a factor graph is a new seam, and it will be
  reached by name from a registry — the case this audit says the gate
  undercounts, so its earning has to be argued by implementers and callers
  rather than by the gate's number.
- **The seven `run_*` wrappers** fold onto a `METHODS` mapping, which is a
  registry and not a seam: nothing new is declared, and the count does not
  move.
- **The four surrogate modules** have `bound.Surrogate`, at five named
  consumers and no problem-defining module among them. The fold is a move of
  code between three homes rather than a new abstraction.

## The gap this leaves

Six of sixteen seams are named by a problem. The intents a reader would
expect to call the same way on every problem — **simulate, evaluate, bound,
sample, initialize** — are spanned by `Objective` and `EmissionFamily` and
otherwise by nothing: a caller who has simulated a tree and wants to simulate
a Potts lattice reads two modules and finds two shapes. That is #813's target
stated as a measurement rather than as an impression, and it is what PR 7's
gap table will carry per problem and per family.
